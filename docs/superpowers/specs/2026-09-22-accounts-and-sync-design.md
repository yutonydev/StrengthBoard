# StrengthBoard: accounts and cross-device sync

Date: 2026-09-22
Status: approved in brainstorming, awaiting spec review

## Goal

Signed-in users keep their lifts and sets in their own account, so the same board shows up in any browser on any device. Right now everything lives in one browser's `localStorage`.

## Decisions

| Topic | Decision |
|---|---|
| Backend | Supabase: Postgres, Auth, Row Level Security (RLS). The SPA calls it directly through `@supabase/supabase-js`, with no custom API. |
| Project | A new Supabase project just for StrengthBoard. StrengthAI's project is not touched. |
| Sign-in | Email + password. Email confirmation is on. "Forgot password" sends a reset email. |
| Password entry | Create account and set new password both ask for the password twice. The form is blocked until the two match. |
| Guest use | None. An account is required, and the sign-in screen comes first. |
| Offline | Changes show instantly and go into an upload queue kept on the device. The queue survives reloads and restarts and retries automatically. The last loaded board is cached for offline viewing. |
| Cross-device freshness | The app re-fetches from the account when it opens and when the tab becomes visible again. There are no live (Realtime) updates. |
| Data model | Approach A: one row per lift and one row per set. A single JSON document per user was rejected because two devices would overwrite each other. |
| Hosting | Vercel, deploying from the GitHub repo `yutonydev/StrengthBoard`. |
| Git | Claude stages changes. The user makes all commits. |
| Code style | No comments in source, CSS or config files. |

## 1. Database (`supabase/migrations/001_init.sql`)

### Tables

`exercises`
- `id uuid primary key`, generated by the client (the app already uses `crypto.randomUUID()`)
- `user_id uuid not null default auth.uid() references auth.users on delete cascade`
- `name text not null`, trimmed length 1–60
- `category text null`, length ≤ 24
- `pinned boolean not null default false`
- `position integer not null default 0`, the board order
- `created_at timestamptz not null`, set from the client's `createdAt`
- `updated_at timestamptz not null default now()`, kept current by a trigger
- `unique (id, user_id)`, which the composite foreign key below needs

`sets`
- `id uuid primary key`, generated by the client
- `user_id uuid not null default auth.uid() references auth.users on delete cascade`
- `exercise_id uuid not null`
- `foreign key (exercise_id, user_id) references exercises (id, user_id) on delete cascade`, so a set can only belong to the same user's lift
- `date date not null`
- `weight_kg double precision not null`, 0–1000. Using `double precision` avoids lb→kg→lb rounding drift.
- `reps smallint not null`, 1–100
- `rpe numeric(3,1) null`, 1–10
- `notes text null`, length ≤ 200
- `created_at timestamptz not null`, set from the client's `createdAt`. It orders the sets within a day.
- Index on `(user_id, exercise_id, date)`

`user_settings`
- `user_id uuid primary key default auth.uid() references auth.users on delete cascade`
- `unit text not null default 'lb'`, either `'lb'` or `'kg'`
- `updated_at timestamptz not null default now()`

### Security

RLS is enabled on all three tables. Each table has select, insert, update and delete policies: `using (user_id = auth.uid())`, plus `with check (user_id = auth.uid())` where it applies. The `anon` role gets no access.

### Functions

Both functions are `security invoker`, so RLS still applies.
- `reorder_exercises(ids uuid[])` sets each of the caller's exercises' `position` to its index in `ids`.
- `replace_board(payload jsonb)` deletes all of the caller's exercises (sets cascade), then inserts the exercises and sets in the payload, in one transaction. Import backup, Clear all data, and undo of those two use it.

### Deliberately not enforced

There is no database-level unique constraint on lift names. The app already blocks duplicates locally. A constraint could still break in one case: two devices each add "Squat" while offline. The second upload would be rejected, and the sets logged under it would be rejected with it. Losing sets is worse than having a duplicate lift the user can rename or delete.

## 2. Authentication

- Uses the `supabase-js` session, which it persists and auto-refreshes itself. Each device stays signed in until the user signs out.
- A **sign-in screen** replaces the board whenever there is no session. It has two modes:
  - **Sign in**: email, password, and a "Forgot password?" link.
  - **Create account**: email, password (at least 8 characters), and confirm password. If the two differ, it shows "Passwords don't match" under the confirm field and does not submit. After sign-up it shows a "Check your email to confirm your account" state. Sign-up sets `emailRedirectTo` to `window.location.origin`.
- **Forgot password** asks for an email and calls `resetPasswordForEmail` with `redirectTo: window.location.origin`. When `onAuthStateChange` reports `PASSWORD_RECOVERY`, the app shows **Set new password**: new password and confirm password, with the same matching rule. It then calls `updateUser({ password })`.
- Errors from Supabase (wrong password, unconfirmed email, rate limit) appear as text under the form. They are never shown by color alone.
- The **account menu** in the header shows the user's email and **Sign out**. If the upload queue isn't empty, it asks for confirmation first ("3 changes haven't uploaded yet and will be lost"). Signing out deletes that user's cache and queue from the device.
- Account deletion inside the app is out of scope. Users can be deleted from the Supabase dashboard.

## 3. Sync

### Units

- `src/supabase.ts` creates the client from `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. A legacy anon key works in the same slot.
- `src/sync/remote.ts` maps between app types and database rows (camelCase ↔ snake_case, `weight` ↔ `weight_kg`). It fetches the whole board, paging through `sets` 1000 rows at a time, and sends one `RemoteOp`.
- `src/sync/ops.ts` has `toRemoteOp(action, stateAfter): RemoteOp[]`. It's a pure function and the main unit under test.
- `src/sync/queue.ts` is a persisted FIFO queue with retry. It knows nothing about React.
- `src/sync/useSyncedStore.ts` replaces `useStore`. It keeps the existing `reducer` untouched and wires in the cache, queue, fetch and status.

### RemoteOp mapping

Every op is idempotent, so a retry can never duplicate or corrupt data.

| App action | RemoteOp(s) |
|---|---|
| `addExercise` | upsert exercise, then `reorder_exercises(all ids in new order)` |
| `updateExercise` | update `name`, `category` |
| `deleteExercise` | delete exercise (its sets cascade) |
| `restoreExercise` | upsert exercise, upsert its sets, then `reorder_exercises` |
| `togglePin` | update `pinned`, then `reorder_exercises` |
| `reorder`, `move` | `reorder_exercises(all ids in new order)` |
| `addSet`, `restoreSet` | upsert set |
| `deleteSet` | delete set |
| `settings` with `unit` | upsert `user_settings.unit` |
| `settings` with `theme` | no RemoteOp. Theme becomes device-local under `strengthboard:theme`. |
| `replace` (import, clear, undo of either) | `replace_board(payload)` |

Each op is computed when the change is made, from the state right after it, and stored with the queue entry.

### Queue entries and storage

Each entry is `{ id, action, ops, attempts }`. Two keys per user are kept in `localStorage`:
- `strengthboard:cache:<userId>`: the last board fetched from the account
- `strengthboard:queue:<userId>`: the pending entries

The old `strengthboard:v1` key is no longer read.

### Load and refresh

1. Once there's a session, render the cached board right away, with the pending queue replayed on top.
2. Fetch the account's board.
3. Set the displayed state to `pendingActions.reduce(reducer, serverBoard)`, so local changes that haven't uploaded yet never disappear from the screen. Cache the server board.
4. Repeat steps 2–3 on `visibilitychange` → visible and on `online`.

### Uploading

- Entries drain one at a time, in order. The next entry starts only after the previous one succeeds.
- **Network errors, timeouts and 5xx responses**: retry with backoff (2 s, 4 s, 8 s … up to 60 s). Retry immediately on `online` and when the tab becomes visible.
- **401 or an expired session**: pause until `supabase-js` refreshes the session or the user signs in again.
- **Other 4xx responses** (a constraint or validation failure): remove that entry, show a toast ("Couldn't save: …"), and keep draining. Then re-fetch, so the screen matches the account.

### Sync status

A header element shows an icon and text, never color alone:
- **Saved**: queue empty
- **Saving…**: an upload is in progress
- **Offline · N waiting**: `navigator.onLine` is false and the queue isn't empty
- **Couldn't save · retrying**: the last attempt failed and a retry is scheduled

## 4. UI changes

- `App` renders `AuthScreen` when there is no session, and the board when there is one.
- The header gains the sync status and the account menu. The existing ⋯ data menu keeps Export, Import and Clear all data. Import and Clear now go through `replace_board`, each with an undo toast as today.
- The theme toggle reads and writes `strengthboard:theme`. The pre-paint script in `index.html` reads the same key.
- The lb/kg toggle dispatches `settings` as today, and the unit syncs.
- New components follow the existing tokens (StrengthAI palette), form styles (`.field`, `.label`, `.btn`) and accessibility rules: visible labels, errors next to their field, focus management.

## 5. Setup and hosting (user steps, documented in the README)

1. Create a Supabase project named StrengthBoard.
2. SQL editor: paste and run `supabase/migrations/001_init.sql`.
3. Auth → URL configuration: set the Site URL to the Vercel URL, and add `http://localhost:5173` and the Vercel URL to Redirect URLs.
4. Copy the project URL and publishable key into `.env.local`. Commit only `.env.example`; `*.local` is already git-ignored.
5. Vercel: import `yutonydev/StrengthBoard`, add both env vars, and deploy. No `vercel.json` is needed, because the app has a single route.

## 6. Testing

- **Unit (vitest):**
  - `toRemoteOp` for every action type
  - The queue: order, persistence across re-creation, retry and backoff classification, dropping on 4xx, pausing on 401
  - Replaying pending actions over a server board
  - The password-match validator
  - The existing 15 tests still pass
- **End-to-end** against the real project, in the browser:
  - Sign up with password mismatch, then a matching password
  - Confirm the email, sign in
  - Log sets, reload, and check they persist from the account
  - A second browser session sees them
  - Go offline (DevTools), log a set, see "Offline · 1 waiting", come back online, and it uploads
  - A second account cannot see the first account's data
  - Forgot password end to end

## Out of scope

Live (Realtime) updates, Google or other OAuth, guest mode, account deletion in the app, and automatic migration of existing local browser data (use Export → Import).
